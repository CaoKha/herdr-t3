# Where data lives, how it is named, how it is read and written

Any data in the layout that has to outlive the current frame is stored, named, read and written as this file says. This file is the single source: to add a kind of data or rename a key, change it here first.

## Six places

Ask two things first: who needs to see it, and how long it has to last. The answers decide where it lives.

| Where | What | Who sees it | How long | Examples |
|---|---|---|---|---|
| Terminal labels | Facts about one terminal (agent) | Every window, every machine | As long as the terminal | `settled`, `snoozed` (no prefix, an exception to the naming rule, unlike `herdr.seen`, `pi.session`) |
| Shared state `shared()` | Data several mods on this machine share | Every mod and window on this machine | Survives restarts | `t3.pins`, `t3.settings` |
| `localStorage` | One mod's own UI state (folding, filters, stash open or closed) | Only this mod copy | Survives restarts | Inbox's `scope`, `settled.open` |
| Memory | What this run remembers | Only this mod copy | Gone on restart | `navigation.js`'s `trail`, `lastIn`, `fresh` |
| Layout file | Layout fields no Herdr command can change | Herdr | Until the next update overwrites it | `traffic_lights`, the sidebar node's `min` |
| User folder | Files the user puts in, and caches generated from them | The mod reading it, and the user | Until the user deletes it | `<appHome>/asciicn-wallpaper/*.ans` |

- **Terminal labels** are written only through `writeLabel` in `shared/labels.js`: it reports errors one way (`Couldn't update the agent`) and returns whether the write landed; `quiet` is for writes that retry, warning only on the first failure.
- **Memory**: the code comment says "this run only", with a `shortcut:` note on when to make it persistent where needed.
- `t3-tabs`'s Clean up confirmation scope (sequence number, panes and terminal addresses to close, spaces expected to close with them) stays in this run's memory only, and the next prompt invalidates the old sequence number; what is rechecked on confirm: see [dialogs](specs/dialogs.md#clean-up).
- Inbox's search term and keyboard highlight are used only in the current view's memory. A card's error message comes from that terminal's own report; Git probe results stay in memory per machine and path, and are rechecked after the working directory changes.
- The tab close confirmation scope is kept only in the memory of the `t3-tabs` copy that opened it: the tab, space, set of terminal addresses, and whether the space will close with it. The confirm command carries this prompt's sequence number and consumes the record only on a match. The next close prompt invalidates the old sequence number.
- Spaces' and the standalone Review bar's directory watch tokens, pending `FolderWatch`es and close markers stay in this run's memory only; on cancel the token is removed first, a late result counts only if the token is still its own, and a released watch is not rebuilt.
- **User folders** live at `<appHome>/<purpose>/`, never inside the mod folder: `scripts/update.sh` updates mods with `rsync --delete`, which would wipe them. Generated caches go in hidden subfolders inside it (`asciicn-wallpaper/.tiles/`, `.builtin/`), keyed by the source file's `cksum` plus the generating code's version, with a done marker written last, so a changed source, an interrupted generation or changed generating code all regenerate; when the source is gone, its cache is deleted with it.
- Check mode doesn't touch these files, the Files image cache or the theme export, and doesn't take this run's wallpaper `previewsReady`; only a real window init cleans up leftover caches and drafts. The isolation entry point: see [layout-implementation](layout-implementation.md).
- **The layout file** is written only with `writeTextFile` and `expected`, replacing just that one field in the text and checking the result against the parsed value. `layout.set` clears the click state Herdr remembers (sidebar width, current stack, chosen theme), so it is not used for appearance fields ([ADR 0009](../adr/0009-settings-hold-real-preferences.md)). The two values `t3-chrome` writes itself (`traffic_lights[1]`, the sidebar node's `min`) don't count as user changes: `scripts/update.sh` skips them when checking whether the file was changed before swapping the layout, because the new copy writes them as soon as it loads; the swapped-in layout carries the repo's values and aligns them again after loading. Any other difference still stops as a conflict.

### Wallpaper drafts

In the wallpaper folder `<appHome>/asciicn-wallpaper/`:

- `*.ans`: the user's pictures (drawn from images); the name is the wallpaper name (`file:<file stem>`).
- `.tiles/<name>/`: a rebuildable cache. `scene.json` (source `cksum` plus `VERSION`, geometry, `paper`) is written last as the done marker; next to it are composites `<dark|light>-<key hash>-<pixels>.svg`, and one uncoloured template per light/dark mode `tiles-<dark|light>-<hash>.tpl`.
- `.builtin/<id>/`: composites of built-in pictures. Built-in pictures' tiles are in the mod's `scenes/`, read-only.
- `.preview/<draft id>/`: a draft's working folder. One `frame-<n>/` per generation, and every drawn mode stays until Apply or Cancel; reading an image also leaves temporary BMPs.

A composite (`makePicture` in `library.js`) is keyed by "folder, source checksum, light/dark, palette"; the file name carries the key's hash and the long-side pixels the SVG declares ([wallpaper spec](specs/wallpaper.md) "Picture size": steps of 512 device pixels, up to 4096), and it is never rewritten once written, because `image()` caches loaded images by path. So a file on disk with the same key and at least the needed pixels is that picture (the smallest if there are several): saved pictures and built-in ones (whose geometry is known) look for it first and use it directly if it is there, with no conversion after a restart. When a bigger one is needed, the same template is `sed`ed again at the new pixels, while in memory the key still points to the small one and each Home keeps showing it; a smaller need doesn't redo it. Writes go to a temporary name first (in one go up to 1 MiB, otherwise in chunks then joined) and are `mv`ed into place; then the other files of the same folder and light/dark mode (old palettes, other pixels, old names without pixels) are deleted, so each picture keeps at most one light and one dark; the deleted files' keys are invalidated at the same time, because the host won't load from a path that no longer exists, and switching back to that palette redoes it. Only one of a key is made at a time, shared by every Home; one cancelled halfway (draft moved to a new generation, conversion invalidated) isn't recorded and is made again next time. When the folder is cleared, its keys in memory are invalidated with it.

A template is a composite of the same light/dark mode with colours replaced by colour-name placeholders (`@ansi1@`), with its size declared as a fixed 4096, replaced by the needed pixels when `sed` colours it; its name is the hash of "folder, source checksum (`VERSION` included), light/dark": it is written the first time a light/dark mode is drawn (to a temporary name first then `mv`, and the `mv` is the done marker); after that, changing palettes, after a restart too, only `sed`s the placeholders into theme colours to write a new composite, without reading and converting the `.ans` again and without going through JS. When the source changes, the folder is cleared by the reconversion; a different checksum or version gives a different name, so an old template is never used. Each folder and light/dark mode keeps only the newest one, so each picture has at most two, each about the size of one composite (measured in a VM: a 960×384 wide Braille picture's folder 3.0→6.1MB, a 682×384 Dots photo 0.28→0.55MB). When Apply adopts the preview, it `link`s the draft's template over too, and the composite is named by the pixels it was made at.

Importing an image first builds an in-memory draft: decoded pixels, sampling plan, mode, generation, request identity, relative framing and `draft.savedName` are not persisted ahead of time. Images default to Dots; switching modes only redraws from the same pixels without rereading the original; drawn modes stay in `draft.frames` and are reused when switching back; a new generation cancels old jobs, and a late result is dropped after checking the draft and generation. `draft.savedName` records only the `.ans` this draft itself published: when the final cache fails, Apply keeps the draft and the published source; a retry reuses only a file it recorded itself whose content matches the draft exactly, otherwise it saves under another name by the no-overwrite rule. Each run, the copies share `previewsReady` and clear last run's leftover `.preview/` once before the first draft is built; after that each clears only its own folder.

A new image's `.ans` starts with a non-drawing OSC `ESC ] 777;asciicn-wallpaper;image-v4;<dots|blocks|quadrants|braille> BEL`, recording the 0.5 cell aspect ratio, the 8-step/VGA theme mapping and the mode; in v4 opaque spaces carry colour too. Light-theme compositing uses it to invert glyphs and step them by darkness (paper), with no need for the original image and no extra file. Reading accepts only the complete start marker and strips it; an `.ans` without it (exported by asciicn Studio, hand-written, `image-v3`) fails to convert, warns once, is recorded as failed in `scene.json`, and isn't listed. Built-in pictures are ready-made tiles in the mod's `scenes/` and aren't converted.

Previews don't write an `.ans` and don't change the shared `asciicn-wallpaper.scene`. **Apply** saves the `.ans`, and only once its composite and `scene.json` are ready does it write the framing, update the selection and clear the draft. When the preview for the current theme is already made, Apply `link`s it into `.tiles/<name>/` before the `.ans` appears (named by the saved scene's key) and writes `scene.json` (the staged text's `cksum`), so scanning the `.ans` needs no conversion; if this step fails or the theme has changed, it converts as usual. **Cancel** keeps the previous selection, framing and files, including an `.ans` a failed Apply already published. Only the generated picture is saved; the original image is never copied or changed. The framing button opens a draft for any picture (built-in or imported) from its existing composite and saved framing (`draft.saved`), without reading files or converting; Apply only writes the framing table and the selection. Delete (Delete in the framing card's footer, imported pictures only) shows the file name and asks again first; cancelling leaves files, caches and framing untouched. A listed picture being reconverted stays in the display list with a `redrawing` mark (Home keeps the previous one, the framing button is disabled), and leaves it only when conversion fails or it is deleted (by another Home too); a confirmed delete doesn't depend on this list; it invalidates that picture's in-flight conversion and pending Apply, and a source being published is deleted only after it finishes writing. Cancel markers stay in memory with the job and are released when the job ends, so old and new jobs never write the same cache in parallel. A late result can't publish a scene, selection or framing, and can't leave a rebuilt cache behind.

`shared("asciicn-wallpaper.placements")` is the only persistent framing table this mod writes, keyed by an imported picture's `file:<file stem>` or a built-in's id (like `lighthouse`), with values `{ mode: "cover" | "contain", zoom: 1..4, x: 0..1, y: 0..1 }`. x/y are the alignment ratio within the space left between the canvas and the scaled image; 0/0 is top left, 0.5/0.5 centred, 1/1 bottom right. Canvas/sidebar size changes and theme switches only recompute geometry from the same parameters, without reconverting the character art. Reads take finite numbers and clamp their range; with no record, the old wallpaper's subject focus and fill rule are kept. Framing is independent of the rebuildable `.tiles/` cache; a confirmed delete clears its entry, as does an external source file disappearing (only `file:` keys; built-in framing is always kept); if a newer framing is committed after a scan starts, the old scan must not delete the new record. Drag, zoom and reset change only the draft, never the shared table or files. Reset keeps the current mode, returns to 1×, and takes the picture's subject focus for x and 0.5 for y.

User file names keep valid Unicode, leading dashes and ordinary hidden names; file listing and checksum metadata are NUL-separated, and file paths are passed as arguments, not options. An `.ans` whose stem is empty, `.` or `..` (`.ans`, `..ans`, `...ans`) is safely refused and can't be used as a `.tiles/` cache folder; ordinary hidden files like `.hidden.ans` are supported as usual. The converter uses tiles of size 40, so expanded shadow shapes stay under 1MiB per write; a version key mismatch only rebuilds the cache, never the source file or framing.

When Apply saves, it writes the text in an exclusive `.preview/save-<unique-id>` (in one write up to 1 MiB; otherwise in chunks under `<it>.parts/`, at most 64K Unicode characters each, below `writeTextFile`'s 1 MiB limit, then joined into the full file), then publishes the target `.ans` atomically with POSIX `link`; an existing file, symlink or folder is never overwritten. On success or failure it cleans up its own save folder, and the source image and other drafts stay untouched.

A confirmed delete first waits for an already started publish of the same name to settle before deleting the file, so a publish never lands after the delete; a waiting retry that receives the delete's cancel marker can't publish the source anymore. Publish promises and Apply cancel markers stay in this run's memory only and are released when the job ends.

### Theme export

`t3-theme-export` starts from a visible zero-height block, and the file `~/.cache/herdr-app-theme.json` is the interface for consumers like Pi: `{name, colors}` comes from the current `settings().theme` and the `theme()` in effect. One copy runs only one write loop; it reads the old text first and writes with the expected value only when the content differs. After a success it rereads the colours, merging changes made during a slow write into the latest snapshot; a conflict or failure retries at the next refresh. `checking()` doesn't read or write this file.

## Shared state key names

Every data-carrying key of the layout mods (`mods/`) is listed in `KEY` in `shared/store.js`; code writes only `KEY.<name>`, never a literal; mods in `extras/` manage their own keys by the same naming rule; `review.shown` and `review.status`, which the layout also reads, are named once in `shared/panel.js` (`REVIEW_SHOWN`, `REVIEW_STATUS`). Names follow the writer:

- **`<mod>.<name>`**: only one mod writes it, others may read it. `t3-tabs.home`, `t3-inbox.rows`.
- **`t3.<name>`**: several mods write it, or it belongs to the whole layout. `t3.pins`, `t3.notice`, `t3.settings`.
- `<name>` is lowerCamel: `t3.spaceIcons`, `t3.agentOrder`.

Two kinds are named by convention and don't go into `KEY`:

- **Popup close timestamps**: when the whole mod is one popup, `<mod>.closed` (`t3-picker.closed`); when the mod is normally something else and also opens as some popup, `<mod>.<that popup>Closed` (`t3-agents.sortClosed`, `t3-menu.spaceClosed`). Key names are generated only by `closedKey(mod, popup?)` in `shared/store.js`, with no literal on either the read or write side (`check-store.cjs` scans for it). The popup's `close()` writes it, and the control that opens it reads it through `shared/trigger.js` (internally `focus.js`'s `justClosed`); the button's on state is also derived by comparing it with the open time. Layers inside Review pages aren't mod popups; when an outside press closes one, the page writes `review.<name>Closed` (`settingsClosed`, `scopeClosed`, etc.).
- **Keys whose names someone else decides** are used as is: `layout`, `space.colors`, `agents.sort`, shared with Herdr's own mods; Inbox's mod card convention `<mod>.program`, `<mod>.status`, `<mod>.titles`.

Review's tree menu is also this mod's native popup and reuses `shared/menus.js`: closing the top level writes `closedKey("review", "menu")`, a submenu writes `closedKey("review", "submenu")`. The opening row's id/time is recorded for this run only; the path, source space/tab and delete marker travel only in popup props and don't change the current file or viewed state.

## Reading and writing

- Data several mods read and write goes through one module in `shared/`, which also holds its defaults: pins through `shared/pins.js` (`pinList`, `pin`, `unpin`, `putBack`, `prunePins`), layout settings through `shared/layout-settings.js`, the Undo notice and undo queue through `shared/notice.js` (`rememberNotice`, `forgetNotice`, `undoNotice`). So Pin ends Snooze wherever it is clicked, and both Inbox and Agents clear pins of finished agents; Undo, whether from an Inbox card, a menu or a shortcut, shares one queue, can merge like operations, and undoes immediately when the sidebar is hidden.
- A key only one mod reads and writes is written in that mod as `shared(KEY.x) ?? default`; JSON `localStorage` is always read tolerantly through `readLocal` in `shared/store.js`.

`t3.settings` defaults to `{ afterAway: "home", homeMod: "t3-home", textSize: null }`; Terminal is stored as `homeMod: null`, and Herdr's interface size as `textSize: null`. `t3.projects` stores Project records of non-Home Spaces that have been opened, `[{ machine, folder, name, named? }]` (not the unnamed local `~` space, even if its terminal `cd`s elsewhere; the active one first, at most 50), written by the resident `t3-tabs` (not written when unchanged), read by `t3-new-menu`, which writes back through `forgetProject` in `shared/projects.js` when removing a remembered project. `t3.notice` stores only display metadata `{ action, count, gen, shown, live, at }`; this run's undo callbacks and timers stay only in `globalThis.t3Notice`, and undo snapshots never go to disk. `t3-actions.actions` is `{ list: [{ id, name, command, icon, place, cwd? }], last }`, one global copy. `t3-inbox.rows` and `t3-agents.rows` publish the `{ order, view }` each draws, so the previous/next agent keys walk the same order. Restarts keep pins, settings, projects, per-space panels, the Home id, recent panes (`t3-tabs.recent`, at most 30) and terminal labels; the last viewed agent and the close history are memory only.

`t3.homeShown` is the wallpaper image Home is showing right now, `{ path, w, h, right, top, opacity, home }` (Home's logical pixels, `right` and `top` measured from Home's top-right corner, `home` the Home id at write time), written only by `asciicn-wallpaper` and read by `t3-tabs`'s Home row, to draw this row's part of the same image ([ADR 0021](../adr/0021-home-is-one-surface.md)). Each render, the wallpaper writes the layer it actually drew (not one still loading), and only when some field changed. There is one copy per machine, and a pane mod doesn't know which pane it is, so only the one instance the top row reads writes it: Home is showing, and Home's tab holds only this one wallpaper pane. The two wallpapers in a split Home, and wallpapers in other tabs, don't write; otherwise two instances would each write their own framing, and each write would make the other redraw, forever. The guard against stale values is on the reading side: it draws only when Home's tab holds a single `asciicn-wallpaper` pane and `home` equals the current Home id; a stale value read after a restart before the wallpaper's first render is the same image if its path still exists, and draws nothing if not.

`t3.panels[space]` stores only `{ tabs, active, open, wide }`, written by `shared/panel.js`; the add/remove/change rules are pure functions in `shared/surfaces.js`. A tab is `{ id, born, reveal, path?, folder?, trail? }`: `files`, `file:<relative path>` or `review`; a folder tab is also `file:<path>`, with `folder: true` and an optional `trail` (the breadcrumb of the file that opened it); the root is `files`. `born` is the tab instance number (kept monotonically increasing across mod copies through `globalThis.t3LastBorn`, and above the `born` of the space's existing tabs); closing and adding again makes a new instance; each mod compares `born` itself to release an old instance's state, and the panel doesn't write other mods' keys. `reveal` is how many times the tab has been selected; when Files sees it change, it clears the search and locates the file (T3's revealRequestId). A record with no `tabs` starts from an empty list; writes keep only the fields above. The layout's stack child block is only a render slot, and an empty list selects `panel-empty`; stacks in Herdr's own layouts don't have this block, and the panel stores no tabs (`panelState().owns` is false). Project icon probe timestamps are shared per `[machine, folder]` through this run's `globalThis.t3ProjectLooked`, so several mods don't probe the same folder twice.

`t3.openTarget` stores one global target name between Files and details; each run on this machine shares `globalThis.t3OpenInTargets`' `{version:3,promise,names}` for parallel app detection; a new list version replaces the old cache, and an uninstalled target is invalidated and falls back to Finder. The finished list is read-only through knownTargets, so a lost old init job during hot reload doesn't leave Files stuck with only Finder; drawing never waits for the promise or scans apps. Candidates come only from T3's full editor table, with installs looked up through macOS LaunchServices (a GUI process's PATH may lack the CLI); drawing and opening the menu don't scan. The last non-null active terminal (space/tab → terminal/cwd/pane) is kept only in this run's `globalThis.t3TerminalContext`, relying like focus.js on the host currently sharing one JS context; it is removed when the terminal closes. Insert briefly borrows the text clipboard and restores it after pasting; an image clipboard is never overwritten, and anything the user copies during the delay wins.

Files' tree is shared per space, and file reading positions are recorded per tab instance for this run only; per space, only the three most recently shown file tabs keep their preview and Editor, older tabs reread from the top; closing releases immediately. With the page-level bound of the three most recent spaces (see the end of this file), that is at most nine file Editors.

`review.shown[space]` stores `{ root, page, base, label, born? }`; `label` is the Review scope button's text (the title once the commit is read), which the details' Review row copies; `born` is the Review tab instance that wrote it (`surfaceBorn` in `panel.js`, absent in Herdr's own stacks). Review, details and the Review bar accept only the current tab's record, through `reviewShown(space)`. The `review` request `{ space, root, page, base?, n, analyze, born? }` is written only by `reviewRequest` in `panel.js`, and likewise is only taken up by the matching tab; details and the standalone bar go through [`openReview`](specs/space-panel.md#which-repository-review-reads), showing first and then sending the request. Review's in-memory copies are evicted by instance number, and late reads are invalidated.

The per-space repository roots details remembers (`roots` in `review-details.js`) last for this run only, to show before a new menu confirms the repository. The source of details and the standalone Review bar travels only with the job and popup props and isn't persisted; this machine's name is read when the details popup starts.

`globalThis.t3Titlebar` records only the panel width measured this run (t3-chrome's panel header), so opening details by keyboard anchors to the same entry point; with the panel closed, details' position is computed from `panel.js` `windowEndPx` and the layout's `tabs-end-inset`, not measured. Reads and writes go through `shared/titlebar.js` (`notePanelWidth`, `detailsAnchor`); nothing goes to shared state or disk. `globalThis.t3PanelPx` records only this run's `panel` logical pixel width before widening the panel (`shared/panel.js` `setWide`); widening switches to `weight: 1` to fill the work area, and restoring switches back to a fixed width at this value. Files' Insert borrows the clipboard to paste a path, and while in progress records only this run's `globalThis.t3PastePending`, so repeated presses don't leave a half-swapped clipboard; after about 150ms the original clipboard is put back and the flag cleared. Insert refuses paths with control characters, so a paste can't become terminal control input; Copy path still works.

Details records only this run's `globalThis.t3Details.id` (the open details popup). Which of t3-menu's, Files' and details' menus hangs under which is recorded only in this run's `globalThis.t3Popups` (`shared/popup-menu.js`: overlay id → `{ mod, parent, kind, back? }`), used for the open state of rows and splits, closing child menus along with their parent, and handing the keyboard back to the parent when a submenu closes itself (`back`); deleted on close. When the Commits submenu opens, it takes the commits already read from this run's `globalThis.t3DetailsRange` (the open range menu) instead of reading Git again. None of this writes shared preferences. Choosing in the Open in menu only updates the global target name; actually opening happens only on a main button click.

`t3-actions.detailsItems` stores the show/hide preference of each details row: `environment`, `openIn`, `scripts`, `review`. All on by default, only `false` values that differ from the default are stored; Reset clears it. The card's context menu and every details copy share this one record; unknown rows and T3 features without a backend are not stored. With everything hidden, the Choose what to show entry still shows, and Actions data, panel tabs and Git repositories are unchanged.

Details' Review row and the Review page share `shared/review-scope.js` (reading, rows, the Commits submenu's content and keys; the Review page's title, base picker and in-page menus are in its own `scope-header.js`): the scope menu rereads counts, commits and refs every time it opens. `scopeCache` lives only in this run's memory, keyed by repository root and base, holding the last result to show while rereading. A late result applies only if the read token, root, space and chosen base are all unchanged, and is void once the menu closes or is evicted. Choosing a scope writes the `review` request and `review.bases`, and no scope is stored separately. Details' scope menu has no base picker; choosing a scope closes details.

Whether a Markdown file shows its preview or its source is `t3-files.markdown` (`"code"` or `"preview"`, preview when unset), one global copy. Files' selected tree row, the folded set during search, and folder loading/error states live only in this run, not in shared state or on disk. Files' menus are this mod's native popups, registered in `globalThis.t3Popups` (see above); closing the top menu writes `t3-files.menuClosed`, closing a submenu writes `t3-files.submenuClosed` (by the "popup close timestamps" convention). Opening a file from an internal tree selection keeps the search; selecting a tab (`reveal` changes) or the open command clears the search and reveals. After Files opens a file itself, it records the current tab's `id:born:reveal`, so the next frame doesn't treat it as an outside selection. The tree is still shared per space; no per-tab tree copies.

`nameW`/`textW` in `shared/measured-text.js` record only this run's natural width/container width of each text, so the same nameText/named/measuredTooltip can judge truncation. Native layout callbacks are normalised by zoom and don't notify when the width hasn't changed; no estimating from character counts, no remeasuring on every redraw.

## `localStorage` key names

Lowercase words joined by dots, written `<thing>.<state>`: `settled.open`, `repos.folded`; a single word when one is enough: `scope`, `changes`. Each mod copy has its own, so no mod prefix.

Files and Review each store `lines.wrap` (boolean string), `nav.width` (logical px) and `nav.open`. The two pages share the read/write functions, but each only touches its own copy's `localStorage`.

Pull requests store in `sections.open` whether each details section (`stack`, `checks`, `reviewers`, `description`, `comments`) is open, as a JSON object recording only sections the user clicked, shared by all PRs; unrecorded ones follow the default (see [pulls](specs/pulls.md#detail)). Comment and reply drafts live only in this run's memory (`drafts` in `composer.js`, by `owner/repo#n` or `owner/repo#n:<thread>`), kept across redraws, refreshes and PR switches, and deleted only once GitHub accepts them; expanded review threads are also this run only.

Pull requests' `sections.open` also has `passed`: whether the passed and skipped row in Checks is expanded, collapsed until clicked.

Images in PR bodies and comments are downloaded to the app folder's `cache/t3-pulls/` (`image()` only reads files under the app folder), named by the resource id (the UUID in GitHub upload URLs, also present in signed URLs; the hash of the URL when there is no UUID) plus an extension chosen by content type, so a new signature from a new read doesn't download again. A download writes `<id>.part` first and is renamed only if the type is right, otherwise deleted. Which images are downloaded, and which signed URL a failure used, live only in this run's memory (`images`); a copy deletes its own downloads when it stops and clears the whole folder on start (leftovers from a last crash), like Files' `cache/t3-files/`.

Issues (`t3-issues`) follow suit: `sections.open` stores whether its own details sections (`prs`, `description`, `comments`) are open, drafts are kept in this run's memory only, by issue id (plus the thread's first comment id for replies), and images go in `cache/t3-issues/`. The Linear API key lives only in this copy's memory (`null` when not found or rejected); it never goes to shared state, `localStorage`, disk or logs, is never drawn, and is never passed as an argument to any program; each run looks it up again on the first show after start (Keychain, Herdr's environment, login shell). With no key, choosing to view GitHub issues instead is also this run only.

The full space data of both pages is this run's cache, keeping at most the three most recent per page. Older spaces keep only light reading settings like selection, expansion and review scope; file contents, Editors, diff lines, wrapping and layout caches are released. Eviction invalidates async reads already sent; a late result can't refill released data. Both pages use bounded refreshes only while visible, and keep no directory watches that can't be unsubscribed. Closing a space clears its memory records too.
